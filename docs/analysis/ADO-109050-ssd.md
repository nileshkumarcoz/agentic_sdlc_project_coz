## 1. Architecture Overview

The solution follows a **layered, event-driven architecture** embedded within the existing `agentic_sdlc_project_coz` platform. The feature introduces three new backend service modules, two new UI pages/components, and an AI orchestration pipeline that chains document processing with LLM analysis.

## 2. Component Design

### 2.1 Frontend Components

#### `RequirementUploadPage`
- Path: `/projects/{projectId}/requirement-analysis/upload`
- Drag-and-drop multi-file upload zone (react-dropzone).
- File type and size validation on the client side.
- Upload progress indicator with WebSocket/SSE feedback.
- Links to previous analyses for the project.

#### `AnalysisResultDashboard`
- Path: `/projects/{projectId}/requirement-analysis/{analysisId}`
- Tabbed interface: Executive Summary | Requirements | Gap Analysis | Risks | Recommendations.
- Each item shows source reference (document name, page/section).
- Export buttons: Download PDF, Download DOCX.
- Re-run analysis button.
- Severity/priority badges on gaps and risks.

---

### 2.2 Backend Service Modules

#### `DocumentService` — `app/services/document_service.py`
**Responsibilities:**
- Accept multipart file uploads via `POST /api/v1/projects/{projectId}/requirement-docs`.
- Validate file type (whitelist: pdf, docx, doc, txt, md, csv, json) and size.
- Generate a SHA-256 hash of the document for deduplication and audit.
- Store raw files in object storage under `s3://sdlc-docs/{projectId}/{analysisId}/{filename}`.
- Persist document metadata to PostgreSQL `requirement_documents` table.
- Trigger asynchronous analysis job via Celery task queue.

#### `AnalysisService` — `app/services/analysis_service.py`
**Responsibilities:**
- Manage the lifecycle of an analysis run (PENDING → PROCESSING → COMPLETED / FAILED).
- Coordinate the AI Orchestrator pipeline.
- Persist structured analysis results to PostgreSQL.
- Expose `GET /api/v1/projects/{projectId}/requirement-analysis/{analysisId}` for result retrieval.
- Expose SSE endpoint `GET /api/v1/projects/{projectId}/requirement-analysis/{analysisId}/stream` for real-time progress.

#### `ExportService` — `app/services/export_service.py`
**Responsibilities:**
- Render structured analysis output to PDF (WeasyPrint) and DOCX (python-docx).
- Expose `GET /api/v1/projects/{projectId}/requirement-analysis/{analysisId}/export?format=pdf|docx`.

---

### 2.3 AI Orchestrator Pipeline — `app/ai/requirement_analyzer.py`

Built using **LangChain** (or LlamaIndex) with a **map-reduce** chain pattern to handle large documents.

**Pipeline Stages:**

```
Stage 1: Document Parsing
  → PDF: PyMuPDF (fitz) + OCR fallback (pytesseract / AWS Textract)
  → DOCX: python-docx
  → TXT/MD: direct text extraction
  → Output: List[DocumentChunk(text, page_no, section_heading)]

Stage 2: Semantic Chunking
  → Split into chunks ≤ 6000 tokens with 200-token overlap
  → Preserve section boundaries
  → Output: List[Chunk]

Stage 3: Per-Chunk Extraction (MAP phase)
  → Prompt: RequirementExtractionPrompt
  → Extract: functional_reqs, non_functional_reqs, assumptions,
             constraints, dependencies, ambiguities, conflicts
  → Output: List[ChunkAnalysis] (structured JSON via Pydantic output parser)

Stage 4: Aggregation & Deduplication (REDUCE phase)
  → Merge ChunkAnalysis results
  → Deduplicate by semantic similarity (cosine similarity on embeddings)
  → Resolve cross-chunk conflicts
  → Output: AggregatedAnalysis

Stage 5: High-Level Synthesis
  → Prompt: ProjectSummaryPrompt (uses AggregatedAnalysis as context)
  → Generate: executive_summary, business_objectives, project_summary

Stage 6: Gap Analysis
  → Prompt: GapAnalysisPrompt
  → Input: AggregatedAnalysis + SDLC Requirement Checklist
  → Output: List[Gap(type, description, source_ref, severity)]

Stage 7: Risk Identification
  → Prompt: RiskIdentificationPrompt
  → Output: List[Risk(category, description, severity, rationale)]

Stage 8: Recommendations
  → Prompt: RecommendationPrompt
  → Input: List[Gap]
  → Output: List[Recommendation(gap_ref, action, priority)]

Stage 9: Result Assembly
  → Assemble AnalysisResult Pydantic model
  → Persist to DB
  → Emit completion event via SSE
```

## 3. Data Model

```sql
-- Uploaded documents
CREATE TABLE requirement_documents (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id      UUID NOT NULL REFERENCES projects(id),
    analysis_id     UUID REFERENCES requirement_analyses(id),
    filename        VARCHAR(255) NOT NULL,
    file_type       VARCHAR(20) NOT NULL,
    file_size_bytes BIGINT NOT NULL,
    sha256_hash     CHAR(64) NOT NULL,
    storage_path    TEXT NOT NULL,
    uploaded_by     UUID NOT NULL REFERENCES users(id),
    uploaded_at     TIMESTAMPTZ DEFAULT NOW()
);

-- Analysis runs
CREATE TABLE requirement_analyses (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id      UUID NOT NULL REFERENCES projects(id),
    status          VARCHAR(20) NOT NULL DEFAULT 'PENDING',
                    -- PENDING | PROCESSING | COMPLETED | FAILED
    version         INTEGER NOT NULL DEFAULT 1,
    triggered_by    UUID NOT NULL REFERENCES users(id),
    triggered_at    TIMESTAMPTZ DEFAULT NOW(),
    completed_at    TIMESTAMPTZ,
    error_message   TEXT,
    -- Structured JSON output stored as JSONB for queryability
    result          JSONB
);

-- Index for project-level listing
CREATE INDEX idx_analyses_project ON requirement_analyses(project_id, triggered_at DESC);

-- Audit log
CREATE TABLE requirement_analysis_audit (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    analysis_id     UUID REFERENCES requirement_analyses(id),
    event_type      VARCHAR(50) NOT NULL,  -- UPLOAD | ANALYSIS_START | ANALYSIS_COMPLETE | EXPORT
    user_id         UUID REFERENCES users(id),
    document_hash   CHAR(64),
    occurred_at     TIMESTAMPTZ DEFAULT NOW(),
    metadata        JSONB
);
```

## 4. Key APIs / Interfaces

### 4.1 Upload Documents
```
POST /api/v1/projects/{projectId}/requirement-docs
Content-Type: multipart/form-data
Body: files[] (one or more)
Response 202:
{
  "analysis_id": "uuid",
  "status": "PENDING",
  "documents": [{"document_id": "uuid", "filename": "BRD_v2.pdf", "status": "ACCEPTED"}]
}
```

### 4.2 Get Analysis Status & Result
```
GET /api/v1/projects/{projectId}/requirement-analysis/{analysisId}
Response 200:
{
  "analysis_id": "uuid",
  "status": "COMPLETED",
  "version": 1,
  "triggered_at": "ISO8601",
  "completed_at": "ISO8601",
  "result": { /* AnalysisResult schema */ }
}
```

### 4.3 Stream Analysis Progress (SSE)
```
GET /api/v1/projects/{projectId}/requirement-analysis/{analysisId}/stream
Accept: text/event-stream
Events:
  data: {"stage": "PARSING", "progress": 10}
  data: {"stage": "EXTRACTING", "progress": 40}
  data: {"stage": "GAP_ANALYSIS", "progress": 70}
  data: {"stage": "COMPLETED", "progress": 100, "analysis_id": "uuid"}
```

### 4.4 List Analyses for Project
```
GET /api/v1/projects/{projectId}/requirement-analysis?page=1&limit=10
Response 200:
{
  "analyses": [{"analysis_id": "uuid", "status": "COMPLETED", "version": 1, "triggered_at": "ISO8601"}],
  "total": 5
}
```

### 4.5 Export Report
```
GET /api/v1/projects/{projectId}/requirement-analysis/{analysisId}/export?format=pdf
Response 200: application/pdf (binary stream)
Content-Disposition: attachment; filename="analysis_{analysisId}.pdf"
```

### 4.6 Re-run Analysis
```
POST /api/v1/projects/{projectId}/requirement-analysis/{analysisId}/rerun
Response 202:
{
  "new_analysis_id": "uuid",
  "status": "PENDING"
}
```

## 6. Technology Choices

| Layer | Technology | Rationale |
|---|---|---|
| Frontend | React + Next.js (existing platform stack) | Consistency with agentic_sdlc_project_coz UI |
| API Backend | FastAPI (Python) | Async support, existing pattern in repo, Pydantic validation |
| Task Queue | Celery + Redis | Async LLM processing, retries, progress events |
| Document Parsing | PyMuPDF, python-docx, pytesseract | Broad format support, OCR fallback |
| AI Orchestration | LangChain (LCEL chains) | Map-reduce patterns, prompt management, output parsers |
| LLM | Azure OpenAI GPT-4o / OpenAI GPT-4o | Large context window (128K), strong structured output |
| Embeddings | OpenAI text-embedding-3-small | Deduplication, semantic similarity in reduce phase |
| Object Storage | AWS S3 / MinIO (existing) | File storage with presigned URLs |
| Database | PostgreSQL + JSONB (existing) | Flexible schema for analysis results |
| Export | WeasyPrint (PDF), python-docx (DOCX) | Server-side rendering without headless browser |
| Observability | OpenTelemetry + existing logging stack | Trace LLM calls, latency, token usage |

## 7. Prompt Engineering Strategy

All prompts are stored as versioned Jinja2 templates under `app/ai/prompts/`.

**Key prompt files:**
- `requirement_extraction.j2` — Instructs LLM to output structured JSON with FR, NFR, assumptions, constraints, dependencies from a document chunk. Uses JSON schema enforcement via `response_format: {type: json_object}`.
- `project_summary.j2` — Synthesises aggregated data into executive summary and business objectives.
- `gap_analysis.j2` — Compares extracted requirements against an SDLC completeness checklist; flags missing, ambiguous, conflicting items.
- `risk_identification.j2` — Identifies project and requirement-level risks with severity scoring.
- `recommendations.j2` — Generates prioritised, actionable recommendations per identified gap.

**Output Validation:** All LLM responses are parsed via Pydantic models. If parsing fails, a retry with a corrective system message is attempted (max 2 retries) before the stage is marked failed.

## 8. Non-Functional Design

### 8.1 Security
- All file uploads validated for MIME type and scanned for malware (ClamAV integration or AWS GuardDuty).
- Documents stored in private S3 buckets; accessed via short-lived presigned URLs only.
- All API endpoints protected by existing JWT auth middleware.
- LLM API calls routed through backend only — no client-side LLM API key exposure.
- RBAC: Only users with `ANALYST` or `OWNER` role on the project can upload or view analyses.
- Audit logs for every upload, analysis trigger, and export event.

### 8.2 Scalability
- Celery workers horizontally scalable; analysis tasks are stateless.
- LLM calls are parallelised during the MAP phase (async `asyncio.gather` across chunks).
- Rate limiting on upload endpoint (10 uploads/min per user) to protect storage and LLM quota.
- Database `result` JSONB column indexed with GIN index for future search capability.

### 8.3 Observability
- Structured logging (JSON) on all service methods with `analysis_id`, `project_id`, `user_id`.
- LLM call telemetry: latency, token count (prompt + completion), model version, stage name — emitted as OpenTelemetry spans.
- Celery task metrics: queue depth, task duration, retry count — exported to Prometheus.
- Alerting: PagerDuty/Slack alert if analysis failure rate > 5% in a 10-minute window.

### 8.4 Error Handling & Resilience
- Each AI pipeline stage has individual try/except with structured error recording.
- Partial results are saved if intermediate stages succeed; the UI shows completed stages even on partial failure.
- Exponential backoff on LLM API calls (max 3 retries, base 2s).
- Dead-letter queue in Celery for tasks that exhaust retries.

## 10. Test Strategy

### 10.1 Unit Tests
- `test_document_parser.py`: Parse sample PDF, DOCX, TXT fixtures; assert extracted text accuracy and chunk boundaries.
- `test_chunker.py`: Verify chunk sizes stay within token limits; section boundaries preserved.
- `test_analysis_service.py`: Mock LLM responses; verify Pydantic schema validation, status transitions, versioning logic.
- `test_file_validator.py`: Assert rejection of invalid MIME types, oversized files, corrupted files.

### 10.2 Integration Tests
- `test_upload_api.py`: Upload real test documents; assert storage in S3 mock (moto), DB record creation, Celery task enqueued.
- `test_analysis_pipeline.py`: Run full pipeline against a sample BRD with mocked LLM API (pre-recorded responses); assert all 7 output sections populated with correct schema.

### 10.3 AI Quality Tests (Benchmark Suite)
- Maintain a `tests/benchmarks/` folder with 5–10 annotated BRD/SRS test documents.
- Ground truth annotations for functional requirements, gaps, risks.
- Precision/recall metrics computed post-analysis; CI gate at ≥ 85% precision (NFR8).
- Run on every PR touching `app/ai/` or `app/ai/prompts/`.

### 10.4 End-to-End Tests (Cypress)
- `test_requirement_analysis_flow.cy.ts`: Upload a DOCX, wait for SSE COMPLETED event, verify all 5 tabs populated, download PDF export, assert non-empty file.

### 10.5 Performance Tests
- Locust load test: 50 concurrent analysis triggers on a 20-page PDF; assert P95 completion < 60s.

### 10.6 Security Tests
- OWASP ZAP scan on upload endpoint for file upload vulnerabilities.
- Assert presigned S3 URLs expire within 15 minutes.
- Assert unauthenticated requests return 401; cross-project access returns 403.
