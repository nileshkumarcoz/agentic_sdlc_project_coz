## 2. Components

### 2.1 Frontend (React SPA — `agentic_sdlc_project_coz/frontend`)
- **Document Upload Widget**: Drag-and-drop, accepts PDF/DOCX/TXT, max 50 MB, shows upload progress.
- **Generation Progress Panel**: Real-time SSE stream showing extraction → story generation → prioritisation → estimation steps.
- **Story Review Board**: Kanban-style card per story showing title, full story text, AC list, priority badge, story-point badge, traceability source ref, and confidence score.
- **Inline Edit**: PO can edit any field; accept (✓) or reject (✗) each card.
- **Batch Actions**: Accept All / Reject All with filter by priority.

### 2.2 API Gateway (`agentic_sdlc_project_coz/api_gateway`)
- JWT validation (existing auth middleware).
- Rate limiting: 10 concurrent document jobs per tenant.
- Routes: `/api/v1/documents`, `/api/v1/stories`, `/api/v1/stories/{id}`.

### 2.3 Story Generation Service (`agentic_sdlc_project_coz/services/story_generator`)
Core backend service, broken into four modules:

| Module | Responsibility |
|--------|----------------|
| `doc_parser` | Converts PDF/DOCX/TXT to structured markdown chunks using `PyMuPDF` + `python-docx`. |
| `requirement_extractor` | Uses LLM + prompt to classify and extract business vs. functional requirements from chunks. |
| `story_builder` | Calls LLM to generate story text, GWT acceptance criteria, priority, story points, and confidence. |
| `traceability_mapper` | Attaches source document section reference to each story. |

### 2.4 LLM Orchestration Layer
- Built with **LangChain** chains + custom `AgentExecutor`.
- Uses structured output parsing (`Pydantic` schemas) to enforce JSON responses.
- Implements chunking (max 3 000 tokens per chunk, 200-token overlap) and map-reduce for large documents.
- Prompt templates stored in `agentic_sdlc_project_coz/prompts/` as versioned YAML files — configurable without code changes (NFR-07).

### 2.5 Document Store
- AWS S3 (or equivalent object store already in platform).
- Server-side encryption (AES-256).
- Pre-signed URL for upload; documents deleted after configurable retention period.

### 2.6 Backlog Database (PostgreSQL)
- Stores projects, documents, requirements, stories, acceptance criteria, and audit events.

### 2.7 Audit & Metrics
- Structured JSON logs shipped to ELK / CloudWatch.
- Metrics: token usage, latency per stage, acceptance rate, error rate — exposed as Prometheus metrics.

## 3. Data Model

```sql
-- Core entities
CREATE TABLE documents (
 id UUID PRIMARY KEY,
 project_id UUID NOT NULL,
 uploaded_by UUID NOT NULL,
 file_name TEXT,
 s3_key TEXT,
 status TEXT, -- PENDING | PROCESSING | DONE | FAILED
 created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE requirements (
 id UUID PRIMARY KEY,
 document_id UUID REFERENCES documents(id),
 req_type TEXT, -- BUSINESS | FUNCTIONAL
 source_section TEXT,
 raw_text TEXT,
 created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE user_stories (
 id UUID PRIMARY KEY,
 requirement_id UUID REFERENCES requirements(id),
 project_id UUID NOT NULL,
 role TEXT,
 capability TEXT,
 business_benefit TEXT,
 priority TEXT, -- HIGH | MEDIUM | LOW
 story_points INT,
 confidence_score NUMERIC(4,3),
 status TEXT, -- DRAFT | ACCEPTED | REJECTED
 created_at TIMESTAMPTZ DEFAULT NOW(),
 updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE acceptance_criteria (
 id UUID PRIMARY KEY,
 story_id UUID REFERENCES user_stories(id),
 given_clause TEXT,
 when_clause TEXT,
 then_clause TEXT,
 display_order INT
);

CREATE TABLE ai_audit_log (
 id UUID PRIMARY KEY,
 user_id UUID,
 document_id UUID,
 action TEXT,
 model_version TEXT,
 token_usage INT,
 latency_ms INT,
 created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## 4. Key APIs

### 4.1 Upload Document
```
POST /api/v1/documents
Content-Type: multipart/form-data
Body: { file, project_id }
Response 202: { document_id, status: "PENDING" }
```

### 4.2 Trigger / Poll Generation
```
POST /api/v1/documents/{document_id}/generate
Response 202: { job_id }

GET /api/v1/documents/{document_id}/stories
Response 200: [
 {
 "story_id": "uuid",
 "requirement_id": "uuid",
 "source_section": "Section 3.2",
 "role": "Product Owner",
 "capability": "upload requirement documents",
 "business_benefit": "reduce manual backlog effort",
 "full_text": "As a Product Owner, I want ...",
 "priority": "HIGH",
 "story_points": 5,
 "confidence_score": 0.87,
 "status": "DRAFT",
 "acceptance_criteria": [
 { "given": "...", "when": "...", "then": "..." }
 ]
 }
]
```

### 4.3 Accept / Reject / Edit Story
```
PATCH /api/v1/stories/{story_id}
Body: { status: "ACCEPTED" | "REJECTED", role?, capability?, story_points?, priority?, acceptance_criteria? }
Response 200: { story_id, status, updated_at }
```

### 4.4 Real-time Progress (SSE)
```
GET /api/v1/documents/{document_id}/progress
Accept: text/event-stream
Events: { stage: "EXTRACTING" | "GENERATING" | "ESTIMATING" | "DONE", progress_pct: 45 }
```

## 6. Prompt Design (Versioned YAML — `agentic_sdlc_project_coz/prompts/`)

### `requirement_extraction_v1.yaml`
```yaml
system: |
 You are a senior business analyst. Extract all requirements from the provided text.
 Classify each as BUSINESS or FUNCTIONAL. Return valid JSON only.
user: |
 Document chunk:
 ---
 {chunk_text}
 ---
 Return a JSON array: [{"req_type": "BUSINESS|FUNCTIONAL", "source_section": "...", "raw_text": "..."}]
```

### `story_generation_v1.yaml`
```yaml
system: |
 You are an expert Agile coach. Given a requirement, generate a user story with:
 - role, capability, business_benefit ("As a [Role], I want [Capability], so that [Benefit]")
 - 3-5 acceptance criteria in Given/When/Then format
 - priority: HIGH | MEDIUM | LOW based on business impact words
 - story_points: Fibonacci (1,2,3,5,8,13) based on complexity
 - confidence_score: 0.0-1.0
 Return valid JSON only.
user: |
 Requirement type: {req_type}
 Requirement text: {raw_text}
 Source section: {source_section}
```

## 7. Technology Choices

| Layer | Technology | Rationale |
|-------|------------|-----------|
| Backend Service | Python 3.12 + FastAPI | Async support, LangChain native, already in platform |
| LLM Orchestration | LangChain 0.2.x | Chains, structured output, map-reduce, prompt templates |
| LLM Model | Azure OpenAI GPT-4o | Enterprise data privacy controls; existing platform agreement |
| Document Parsing | PyMuPDF (PDF), python-docx (DOCX) | Accurate layout extraction |
| Database | PostgreSQL 16 (existing) | ACID compliance, JSON support, already in platform |
| Object Store | AWS S3 (existing) | Scalable, encrypted, signed URLs |
| Frontend | React 18 + TypeScript (existing) | Consistency with platform UI |
| Real-time Updates | Server-Sent Events (SSE) | Lightweight; no WebSocket infra needed |
| Observability | Prometheus + Grafana / CloudWatch | Existing platform tooling |
| CI/CD | GitHub Actions in `agentic_sdlc_project_coz` | Existing pipeline |

## 8. Non-Functional Design

### 8.1 Security
- Documents uploaded via pre-signed S3 URLs; never pass through API gateway payload.
- All LLM calls routed through Azure OpenAI private endpoint (no public internet).
- PII/sensitive keyword scanner runs pre-LLM to flag or mask sensitive terms.
- JWT-based auth; story access scoped to project membership.
- Secrets managed via AWS Secrets Manager / environment secrets.

### 8.2 Scalability
- Story generation jobs pushed to an async task queue (Celery + Redis or AWS SQS).
- Map-reduce chunking handles documents of any size without hitting token limits.
- Horizontal scaling of FastAPI workers behind load balancer.
- LLM calls use async `aiohttp` for concurrency; connection pool size tuned per quota.

### 8.3 Observability
- `ai_audit_log` table captures every LLM invocation (model version, tokens, latency).
- Prometheus metrics exported: `story_gen_latency_seconds`, `story_acceptance_rate`, `llm_token_usage_total`, `doc_processing_errors_total`.
- Grafana dashboard: real-time acceptance rate trend, average story-gen latency, error spike alerts.
- Structured log fields: `correlation_id`, `document_id`, `user_id`, `stage`, `duration_ms`.

### 8.4 Resilience
- Circuit breaker on LLM API calls (3 failures → open circuit → return graceful error).
- Retry with exponential backoff (max 3 retries) for transient LLM errors.
- Document processing status persisted in DB; failed jobs can be requeued without re-upload.

## 10. Test Strategy

| Layer | Type | Tooling | Key Scenarios |
|-------|------|---------|---------------|
| Unit | Doc parser | pytest | PDF/DOCX/TXT parsing; malformed file handling |
| Unit | Requirement extractor | pytest + LLM mock | Correct classification; empty document; oversized chunk |
| Unit | Story builder | pytest + LLM mock | Valid JSON output; missing fields; confidence threshold |
| Integration | API endpoints | pytest + TestClient | Upload → generate → retrieve full flow |
| Integration | DB | pytest + test DB | Schema constraints; cascaded deletes |
| Contract | LLM structured output | pytest | Pydantic validation of LLM response schema |
| E2E | Full workflow | Playwright | Upload doc → review board populated → accept stories → appear in backlog |
| Performance | Load test | Locust | 50 concurrent users; p95 < 60 s for 20-page doc |
| Security | SAST | Bandit + Semgrep | Secrets in code; injection; insecure deserialization |
| AI Quality | Acceptance rate | Manual PO review (first 3 sprints) | ≥ 85 % story acceptance without major edits |
