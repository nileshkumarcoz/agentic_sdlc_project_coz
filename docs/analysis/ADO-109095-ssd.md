## 2. Components

### 2.1 TestCaseGenerationAgent (New Agent)
Located in: `agents/test_case_generation_agent.py`

Extends the existing base `SDLCAgent` class in the repository. Orchestrates four specialised tools in sequence:

| Tool Class | Responsibility | Prompt Template File |
|-----------|---------------|---------------------|
| `StoryAnalyserTool` | Extract actors, functional actions, AC items, constraints | `prompts/story_analyser.jinja2` |
| `TestCaseBuilderTool` | Generate positive & negative test cases per AC item | `prompts/test_case_builder.jinja2` |
| `EdgeCaseIdentifierTool` | Apply boundary value and equivalence partition analysis | `prompts/edge_case_identifier.jinja2` |
| `TestDataRecommenderTool` | Recommend valid/invalid data sets per scenario | `prompts/test_data_recommender.jinja2` |

### 2.2 LLM Service Adapter (Extended)
Existing `services/llm_service.py` extended with:
- `generate_with_schema()` method enforcing JSON-schema structured output.
- Token budget guard (max tokens per story configurable via env var `MAX_TOKENS_PER_STORY`).
- Response caching keyed on SHA-256 of (story_id + story_content_hash) to avoid redundant LLM calls.

### 2.3 API Layer (FastAPI — Extended)
New router: `routers/test_cases.py`
- `POST /api/v1/stories/{story_id}/generate-test-cases`
- `GET /api/v1/stories/{story_id}/test-cases`
- `PATCH /api/v1/test-cases/{tc_id}` (QA review: approve/reject/edit)
- `GET /api/v1/stories/{story_id}/coverage-report`

### 2.4 Event Trigger (Celery Task)
New Celery task `tasks/test_case_generation_task.py`:
- Subscribes to `story.approved` event on the existing event bus.
- Instantiates `TestCaseGenerationAgent` and invokes `.run(story_id)`.
- Supports both event-driven and on-demand invocation paths.

### 2.5 UI Components (React — Extended)
New pages/components:
- `TestCaseReviewPage` — lists generated test cases per story in a filterable table.
- `TestCaseCard` — editable card with approve/reject/edit actions.
- `CoverageReportWidget` — doughnut chart of AC coverage + gaps list.

## 3. Data Model

### 3.1 `test_cases` Table
```sql
CREATE TABLE test_cases (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    story_id          VARCHAR(50) NOT NULL REFERENCES user_stories(id),
    ac_reference      VARCHAR(100),          -- e.g. "AC1", "AC2"
    title             TEXT NOT NULL,
    preconditions     TEXT,
    test_steps        JSONB NOT NULL,         -- [{step, action, expected_result}]
    expected_result   TEXT NOT NULL,
    test_type         VARCHAR(20) NOT NULL    -- 'positive'|'negative'|'edge'|'boundary'
                      CHECK (test_type IN ('positive','negative','edge','boundary')),
    test_data         JSONB,                  -- [{label, value, reason}]
    status            VARCHAR(20) DEFAULT 'draft'
                      CHECK (status IN ('draft','approved','rejected')),
    generation_run_id UUID NOT NULL,
    generated_at      TIMESTAMPTZ DEFAULT NOW(),
    reviewed_by       VARCHAR(100),
    reviewed_at       TIMESTAMPTZ,
    version           INT DEFAULT 1,
    created_at        TIMESTAMPTZ DEFAULT NOW(),
    updated_at        TIMESTAMPTZ DEFAULT NOW()
);
```

### 3.2 `test_generation_runs` Table
```sql
CREATE TABLE test_generation_runs (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    story_id        VARCHAR(50) NOT NULL,
    triggered_by    VARCHAR(100),   -- 'auto'|user_id
    model_version   VARCHAR(50),
    prompt_hash     VARCHAR(64),
    status          VARCHAR(20),    -- 'running'|'completed'|'failed'
    tc_count        INT,
    error_message   TEXT,
    started_at      TIMESTAMPTZ DEFAULT NOW(),
    completed_at    TIMESTAMPTZ
);
```

### 3.3 `ac_coverage` View
```sql
CREATE VIEW ac_coverage AS
SELECT
    story_id,
    ac_reference,
    COUNT(*) FILTER (WHERE test_type = 'positive')  AS positive_count,
    COUNT(*) FILTER (WHERE test_type = 'negative')  AS negative_count,
    COUNT(*) FILTER (WHERE test_type IN ('edge','boundary')) AS edge_count,
    COUNT(*) TOTAL
FROM test_cases
WHERE status != 'rejected'
GROUP BY story_id, ac_reference;
```

**Request:**

```json
  "test_steps": [...]

```

### 4.4 Agent Internal Interface — `TestCaseGenerationAgent.run()`
```python
class TestCaseGenerationAgent(BaseSDLCAgent):
    def run(self, story_id: str, options: GenerationOptions) -> GenerationResult:
        story = self.story_repo.get_approved(story_id)
        analysis = self.story_analyser_tool.run(story)
        test_cases = self.test_case_builder_tool.run(analysis)
        edge_cases = self.edge_case_identifier_tool.run(analysis)
        test_cases_with_data = self.test_data_recommender_tool.run(
            test_cases + edge_cases
        )
        return self.persist_and_return(story_id, test_cases_with_data)
```

## 5. Main Flow — Sequence Diagram

```
QA Engineer / Event Bus
        │
        │ 1. POST /generate-test-cases (or story.approved event)
        ▼
   API Gateway (FastAPI)
        │ 2. Enqueue Celery task
        ▼
   Celery Worker
        │ 3. Instantiate TestCaseGenerationAgent
        ▼
   TestCaseGenerationAgent
        │ 4. Fetch story from Stories DB
        │ 5. StoryAnalyserTool → LLM (prompt: extract actors, ACs, rules)
        │    ← Structured JSON: {actors, ac_items, constraints}
        │ 6. TestCaseBuilderTool → LLM (prompt: generate +ve/-ve per AC)
        │    ← [{tc_id_temp, ac_ref, title, steps, type}]
        │ 7. EdgeCaseIdentifierTool → LLM (prompt: boundary/equiv analysis)
        │    ← [{tc_id_temp, ac_ref, title, steps, type='edge'/'boundary'}]
        │ 8. TestDataRecommenderTool → LLM (prompt: valid/invalid data)
        │    ← test_cases enriched with test_data[]
        │ 9. Persist all test cases → TestCases DB (status='draft')
        │ 10. Update generation_run record (status='completed')
        │ 11. Emit test_cases.generated event (WebSocket push to UI)
        ▼
   QA Engineer UI
        │ 12. Review test cases in TestCaseReviewPage
        │ 13. PATCH /test-cases/{id} (approve/edit/reject)
        ▼
   API Gateway → DB update (status='approved'/'rejected')
        │
        │ 14. GET /coverage-report → aggregated from ac_coverage view
        ▼
   QA Engineer views coverage dashboard
```

## 6. Prompt Engineering Design

### 6.1 StoryAnalyser Prompt (`prompts/story_analyser.jinja2`)
```
System: You are a senior QA analyst. Extract structured information from the following user story.
Return ONLY valid JSON matching this schema: {actors:[], functional_actions:[], ac_items:[{id,given,when,then}], business_rules:[], constraints:[]}.

User Story:
Title: {{ story.title }}
Description: {{ story.description }}
Acceptance Criteria: {{ story.acceptance_criteria }}
```

### 6.2 TestCaseBuilder Prompt (`prompts/test_case_builder.jinja2`)
```
System: You are a QA expert. Given the extracted requirements below, generate comprehensive test cases.
For EACH acceptance criterion, produce at least 2 positive and 2 negative test cases.
Return JSON array: [{ac_reference, title, preconditions, test_steps:[{step,action,expected_result}], expected_result, test_type}]

Extracted Requirements: {{ analysis | tojson }}
```

### 6.3 EdgeCaseIdentifier Prompt (`prompts/edge_case_identifier.jinja2`)
```
System: You are a boundary-value analysis expert. Analyse the business rules and constraints.
Identify: (1) boundary value cases, (2) equivalence partitions, (3) state-transition edges, (4) error/exception paths.
Return JSON array with test_type set to 'edge' or 'boundary'.

Business Rules & Constraints: {{ analysis.business_rules | tojson }}
Existing Test Cases (for context): {{ existing_cases | tojson }}
```

### 6.4 TestDataRecommender Prompt (`prompts/test_data_recommender.jinja2`)
```
System: For each test case provided, recommend specific test data.
For each, provide valid and invalid data examples with a reason.
Return the same array enriched with test_data:[{label, value, reason, validity:'valid'|'invalid'}].

Test Cases: {{ test_cases | tojson }}
Constraints: {{ analysis.constraints | tojson }}
```

## 8. Non-Functional Design

### 8.1 Security
- All story content sent to LLM passes through the `LLMServiceAdapter` which enforces the org-approved API endpoint (Azure OpenAI private deployment — no data used for training).
- Story content is sanitised to remove any accidentally included PII tokens before prompt construction (`services/pii_sanitiser.py`).
- API endpoints require JWT auth with `role:qa_engineer` or `role:admin` scope.
- Prompt templates are stored in-repo (not user-editable via UI) to prevent prompt injection.

### 8.2 Scalability
- Celery workers are horizontally scalable; each story generation is an independent task.
- Token budgeting: `MAX_TOKENS_PER_STORY=8000` env var prevents runaway LLM spend.
- LLM response caching (Redis, TTL=24 h) avoids re-processing identical story content.
- Database indexes on `(story_id, status)` and `(generation_run_id)` for fast query.
- Batch endpoint `POST /api/v1/stories/batch-generate` accepts up to 50 story IDs, enqueues as separate tasks.

### 8.3 Observability
- Every generation run logged to `test_generation_runs` with model version, prompt hash, duration, token count.
- Structured logs (JSON) emitted at each tool stage: `{event, story_id, tool, duration_ms, token_usage}`.
- Prometheus metrics exported: `tc_generation_duration_seconds`, `tc_generation_total`, `tc_generation_errors_total`, `llm_token_usage_total`.
- Grafana dashboard (existing platform infra) extended with TC Generation panel.
- Alerting: if `tc_generation_errors_total` rate > 5 % over 5 min, alert on-call.

## 9. Test Strategy for This Feature

### 9.1 Unit Tests (`tests/unit/`)
- `test_story_analyser_tool.py` — mock LLM, assert JSON extraction correctness for 10 story fixtures.
- `test_test_case_builder_tool.py` — assert minimum case counts per AC, correct test_type assignment.
- `test_edge_case_identifier_tool.py` — assert boundary cases detected from known business rules.
- `test_data_recommender_tool.py` — assert valid/invalid data present and annotated.
- `test_pii_sanitiser.py` — assert PII tokens stripped before prompt construction.

### 9.2 Integration Tests (`tests/integration/`)
- `test_generation_agent_e2e.py` — use test LLM stub, run full agent pipeline, assert test cases persisted in test DB.
- `test_api_generate_endpoint.py` — POST to generate endpoint, poll for completion, GET test cases, assert schema.
- `test_celery_task.py` — enqueue task, assert completion and DB state.

### 9.3 Contract / Schema Tests
- Pydantic schema validation tests against all four LLM response models.
- JSON Schema snapshot tests for API responses to catch regressions.

### 9.4 Quality / Accuracy Tests (UAT)
- Curated set of 20 reference stories with known expected test cases.
- Automated scoring: % of expected cases present in generated output.
- Threshold: ≥ 85 % recall before feature is considered production-ready.

### 9.5 Performance Tests
- Locust load test: 50 concurrent story generation requests, assert p95 < 30 s.
- Token budget enforcement test: story exceeding budget returns graceful error.

### 9.6 Security Tests
- Prompt injection attempt tests: malicious story text attempting to override system prompt.
- Auth boundary tests: unauthenticated / wrong-role requests return 401/403.
- PII leakage test: story containing mock PII — assert sanitiser strips before LLM call.
