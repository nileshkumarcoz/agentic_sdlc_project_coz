# Solution Design Document
## Story ID: 109110 — Successful User Login

---

### 1. Proposed Architecture Overview

The solution follows a standard **client–server SPA architecture** with a dedicated authentication API endpoint. The frontend is a Single Page Application (SPA) that communicates with a RESTful backend. On successful login, a signed JWT is issued, stored in an HttpOnly cookie, and the SPA client-side router navigates to the landing page.

### 3. Data Model

#### `users` Table (existing, assumed)
```sql
CREATE TABLE users (
 id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
 email VARCHAR(255) UNIQUE NOT NULL,
 password_hash VARCHAR(255) NOT NULL, -- bcrypt hash
 display_name VARCHAR(100) NOT NULL,
 created_at TIMESTAMP DEFAULT NOW(),
 updated_at TIMESTAMP DEFAULT NOW()
);
```

#### JWT Payload
```json
{
 "sub": "<user-uuid>",
 "email": "user@example.com",
 "display_name": "Jane Doe",
 "iat": 1700000000,
 "exp": 1700003600
}
```
- `exp`: 1 hour (configurable via environment variable `JWT_EXPIRY_SECONDS`)
- Signed with HS256 using a secret stored in environment variable `JWT_SECRET`

### 4. Key APIs / Interfaces

#### 4.1 POST `/api/auth/login`

**Request**
```http
POST /api/auth/login
Content-Type: application/json

{
 "email": "user@example.com",
 "password": "plaintextPassword"
}
```

**Success Response — HTTP 200**
```http
Set-Cookie: auth_token=<JWT>; HttpOnly; Secure; SameSite=Strict; Path=/
Content-Type: application/json

{
 "success": true,
 "user": {
 "id": "<uuid>",
 "display_name": "Jane Doe",
 "email": "user@example.com"
 }
}
```

**Failure Response — HTTP 401** *(out of scope for this story but defined for completeness)*
```json
{ "success": false, "error": "INVALID_CREDENTIALS" }
```

#### 4.2 GET `/api/auth/me` *(optional — used if display_name is not embedded in token)*
```http
GET /api/auth/me
Cookie: auth_token=<JWT>

HTTP 200
{ "id": "<uuid>", "display_name": "Jane Doe", "email": "user@example.com" }
```

### 6. Frontend Implementation Details

#### LoginPage Component
```
- Controlled form with email and password fields
- On submit: call authService.login(email, password)
- On success: store user object in global auth context/store; navigate to '/'
- On error: show inline error message (out of scope for this story)
- Accessibility: labels linked to inputs, keyboard-navigable, aria-live for status
```

#### LandingPage Component
```
- Protected route — redirects to /login if no valid auth token
- Reads display_name from auth context
- Renders: <h1>Welcome {display_name}</h1>
- Renders: <NavMenu /> component
```

#### NavMenu Component
```
- Renders list of navigation links as defined in nav config
- Links to be provided by Product Owner (OQ-04)
- Renders only when authenticated
```

#### Auth State Management
```
- Use React Context (or existing state management in repo) to hold { user, isAuthenticated }
- Populated from login API response
- Cleared on logout (future story)
```

### 7. Backend Implementation Details

#### AuthController — `POST /api/auth/login`
```
1. Validate request body (email: valid format, password: non-empty) → 400 if invalid
2. Call AuthService.login(email, password)
3. On success: set HttpOnly cookie with JWT; return 200 + user payload
4. On failure: return 401 (handled in separate story)
```

#### AuthService
```
1. UserRepository.findByEmail(email)
2. If user not found → throw AuthenticationError
3. bcrypt.compare(plainPassword, user.password_hash)
4. If mismatch → throw AuthenticationError
5. Build JWT payload: { sub, email, display_name, iat, exp }
6. Sign with JWT_SECRET → return token + user DTO
```

#### jwtMiddleware
```
- Extracts token from auth_token cookie
- Verifies signature and expiry
- Attaches decoded user to request context
- Returns 401 if invalid/expired
```

### 8. Technology Choices

| Concern | Choice | Rationale |
|---|---|---|
| Password hashing | bcrypt (cost factor 12) | Industry standard, computationally expensive for attackers |
| Token format | JWT (HS256) | Stateless, carries display_name to avoid extra DB call on landing |
| Token transport | HttpOnly Secure Cookie | Prevents XSS-based token theft vs localStorage |
| Input validation | Zod / Joi (per repo convention) | Schema-validated at controller boundary |
| Frontend routing | React Router (or existing router in repo) | Protected route wrapper for landing page |

*Specific library versions to be aligned with existing `package.json` / dependency manifest in `agentic_sdlc_project_coz`.*

### 9. Non-Functional Design

#### Security
- Passwords hashed with bcrypt (cost ≥ 12) before storage; never logged
- JWT signed server-side; secret rotated via environment variable
- Cookie flags: `HttpOnly`, `Secure`, `SameSite=Strict`
- HTTPS enforced at infrastructure level (TLS termination at load balancer or server)
- Input sanitised at controller layer to prevent injection
- Rate limiting on `/api/auth/login`: max 10 attempts per IP per minute (via middleware, to be implemented alongside or as follow-up story)

#### Scalability
- Stateless JWT allows horizontal scaling of backend without shared session store
- DB connection pooling configured in UserRepository
- Login endpoint expected to be low-volume relative to other API calls

#### Observability
- Structured logs emitted on: login attempt (email masked), login success (user id), login failure reason category
- Metrics: `auth_login_success_total`, `auth_login_failure_total`, `auth_login_latency_ms` counters/histograms
- Distributed trace context propagated through request (if tracing is configured in repo)
- Alerts: spike in login failures → potential credential stuffing attack
