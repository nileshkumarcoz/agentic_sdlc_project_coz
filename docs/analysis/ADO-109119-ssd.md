## 5. Data Model

### 5.1 Form Payload (Request Body)
```json
{
 "firstName": "string, required, max 50",
 "lastName": "string, required, max 50",
 "email": "string, required, valid email format",
 "phoneNumber": "string, optional, E.164 format",
 "category": "string, required, enum [value1, value2, ...]",
 "message": "string, optional, max 500",
 "consentGiven": "boolean, required, must be true"
}
```
> **Note**: Exact fields to be confirmed per OQ-01. Schema is illustrative.

### 5.2 API Response — Success (HTTP 201)
```json
{
 "status": "success",
 "submissionId": "uuid",
 "message": "Your information has been received."
}
```

### 5.3 API Response — Validation Error (HTTP 422)
```json
{
 "status": "error",
 "errors": [
 { "field": "email", "message": "Must be a valid email address." }
 ]
}
```

### 5.4 API Response — Server Error (HTTP 500)
```json
{
 "status": "error",
 "message": "An unexpected error occurred. Please try again later."
}
```

### 6.3 Yup Validation Schema (formSchema.js)
```javascript
import * as Yup from 'yup';
export const formSchema = Yup.object({
 firstName: Yup.string().required('First name is required').max(50),
 lastName: Yup.string().required('Last name is required').max(50),
 email: Yup.string().email('Enter a valid email').required('Email is required'),
 phoneNumber: Yup.string().matches(/^[+]?[0-9]{7,15}$/, 'Invalid phone number').optional(),
 category: Yup.string().required('Please select a category'),
 message: Yup.string().max(500).optional(),
 consentGiven: Yup.boolean().oneOf([true], 'You must provide consent'),
});
```

## 8. Non-Functional Design

### 8.1 Security
- All form submissions over **HTTPS only**.
- **CSRF Token**: Read CSRF token from a cookie or `<meta>` tag (set by server) and include as `X-CSRF-Token` header in every POST.
- **Input Sanitisation**: Yup validation on client side; backend must independently sanitise and validate (defence-in-depth).
- **No sensitive data in URL**: Form data submitted as POST body only.
- **Content Security Policy**: Ensure the page's CSP header allows the form action origin.

### 8.2 Accessibility (WCAG 2.1 AA)
- Every `<input>` has an associated `<label>` via `htmlFor`.
- Required fields include `aria-required="true"` and a visible `*` with a legend.
- Validation errors rendered in `<span role="alert">` linked to input via `aria-describedby`.
- Success and error banners use `role="status"` / `role="alert"` for screen reader announcements.
- Full keyboard navigation; no keyboard traps.
- Focus moved to first error field after failed submit.

### 8.3 Responsiveness
- Form layout uses CSS flexbox/grid with breakpoints: mobile-first.
- Single-column layout on mobile; optional two-column on desktop for multi-field rows.
- Touch targets ≥ 44 × 44 px (WCAG 2.5.5).

### 8.4 Observability
- Log `form_submission_attempt`, `form_submission_success`, `form_submission_error` events via the project's existing analytics/logging utility.
- Include `submissionId` in success log for traceability.
- Frontend error boundary wraps `<Form />` to catch unexpected render errors.

### 8.5 Performance
- React Hook Form avoids full re-renders on each keystroke.
- Yup schema compiled once (outside component render).
- Lazy-load `<FormPage />` if not on critical path using `React.lazy`.

## 9. Test Strategy

### 9.1 Unit Tests (Jest + React Testing Library)
| Test Case | Description |
|---|---|
| UT-01 | All fields render with correct labels and placeholders |
| UT-02 | Required field markers (`*`) present on mandatory fields |
| UT-03 | Inline error shown when required field left empty on submit |
| UT-04 | Inline error shown for invalid email format |
| UT-05 | Submit button disabled while request is in-flight |
| UT-06 | `SuccessBanner` renders on mocked 201 response |
| UT-07 | `ErrorBanner` renders on mocked 500 response; form data preserved |
| UT-08 | `formService.submitForm` called with correct payload |
| UT-09 | Yup schema rejects invalid data and approves valid data |

### 9.2 Integration Tests
| Test Case | Description |
|---|---|
| IT-01 | Form submission triggers correct API call with expected headers |
| IT-02 | CSRF token included in request header |
| IT-03 | 422 response maps server-side field errors to form fields |

### 9.3 End-to-End Tests (Cypress)
| Test Case | Description |
|---|---|
| E2E-01 | Happy path: fill all fields, submit, see success banner |
| E2E-02 | Validation path: submit empty form, verify all error messages |
| E2E-03 | Mobile viewport: form renders correctly and is submittable |
| E2E-04 | Keyboard-only navigation: tab through all fields, submit with Enter |

### 9.4 Accessibility Tests
- `jest-axe` assertions in unit tests on rendered form.
- Cypress `cypress-axe` plugin runs on E2E form page.

### 9.5 Cross-Browser
- Cypress tests executed on Chrome, Firefox, and Edge via CI matrix.
- BrowserStack (or equivalent) for Safari validation.
