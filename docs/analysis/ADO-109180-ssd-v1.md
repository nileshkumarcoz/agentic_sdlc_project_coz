# Solution Design Document (SSD)
## Story ID: 109180 — Solution Architecture Generation

---

## 1. Proposed Architecture Overview

The solution introduces a new **Architecture Generation Agent** into the existing agentic SDLC pipeline hosted in `agentic_sdlc_project_coz`. The agent follows the platform's established agent pattern: a dedicated agent module triggered via the orchestration layer, calling an LLM with structured prompts, validating the output, and persisting the result.

## 2. Components

### 2.1 Frontend Components
| Component | Description | Location |
|-----------|-------------|----------|
| **Architecture Generation Page** | Trigger point — user selects a story and uploads/links a requirement document; displays generation status and results | `frontend/src/pages/ArchitectureGeneration/` |
| **SAD Viewer / Editor** | Renders the generated SAD with section-level inline editing; approval/reject actions | `frontend/src/components/SADViewer/` |
| **Document Upload Widget** | Drag-and-drop file uploader; validates file type/size before submission | `frontend/src/components/DocumentUpload/` |
| **Component Tree Panel** | Visual collapsible tree of identified architecture components grouped by category | `frontend/src/components/ComponentTree/` |

### 2.2 Backend Services
| Service | Responsibility | Location |
|---------|---------------|----------|
| **Document Ingestion Service** | Accepts uploaded file, validates, stores in Blob store, extracts raw text (PyMuPDF for PDF, python-docx for DOCX) | `backend/services/document_ingestion/` |
| **ArchGen Agent** | Core agent: calls LLM with structured prompts, validates JSON output schema, maps results to SAD data model | `agents/arch_gen_agent/` |
| **SAD Management Service** | CRUD for Solution Architecture Documents; handles versioning and approval state machine | `backend/services/sad_management/` |
| **Orchestrator** | Existing LangGraph/CrewAI orchestration layer extended with ArchGen workflow | `orchestrator/` |
| **Audit Service** | Writes immutable log records for each agent invocation | `backend/services/audit/` |

### 2.3 Databases
| Store | Technology | Purpose |
|-------|------------|---------|
| **Document Store** | AWS S3 / Azure Blob Storage | Store raw uploaded requirement documents (encrypted at rest) |
| **SAD Store** | PostgreSQL (JSONB columns) | Store structured SAD artefacts, versions, approval status |
| **Audit Log** | PostgreSQL (append-only table) | Immutable agent run logs |
| **Cache** | Redis | Cache LLM responses for identical document hashes; rate-limit guard |

### 2.4 APIs
| Endpoint | Method | Description |
|----------|--------|-------------|
| `POST /api/v1/documents/upload` | POST | Upload requirement document; returns `document_id` |
| `POST /api/v1/architecture/generate` | POST | Trigger architecture generation for a `story_id` + `document_id` |
| `GET /api/v1/architecture/{sad_id}` | GET | Retrieve generated SAD by ID |
| `PUT /api/v1/architecture/{sad_id}` | PUT | Update SAD fields (architect edits) |
| `POST /api/v1/architecture/{sad_id}/approve` | POST | Mark SAD as approved |
| `GET /api/v1/architecture/{sad_id}/versions` | GET | List all versions of a SAD |
| `GET /api/v1/audit/architecture/{sad_id}` | GET | Retrieve audit log for a SAD |

### 2.5 External Integrations
| Integration | Purpose |
|-------------|---------|
| **Azure OpenAI / OpenAI API** | LLM inference for requirement analysis and architecture generation |
| **Existing Auth Provider (OAuth2/OIDC)** | User authentication — reuses platform SSO |
| **Story Management System** | Links generated SAD to the originating story ID (Jira / internal tracker) |

### 2.6 Security Components
| Component | Implementation |
|-----------|---------------|
| **AuthN/AuthZ** | JWT Bearer tokens validated on every API call; RBAC roles: `architect`, `reviewer`, `admin` |
| **Transport Encryption** | TLS 1.2+ enforced on all HTTP endpoints |
| **Data Encryption at Rest** | S3/Blob SSE-AES-256 for documents; PostgreSQL TDE or encrypted volumes |
| **Input Sanitisation** | Strip executable content from documents before LLM submission; prompt injection guard |
| **Secrets Management** | LLM API keys stored in AWS Secrets Manager / Azure Key Vault; injected at runtime |
| **Data Classification Gate** | Pre-flight check flags documents marked CONFIDENTIAL and routes to private/on-prem LLM |
| **Audit Logging** | Append-only log with model version, input hash, user ID, timestamp, output hash |

## 3. Data Model

### 3.1 `requirement_documents` table
```sql
CREATE TABLE requirement_documents (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    story_id      VARCHAR(50) NOT NULL,
    filename      TEXT NOT NULL,
    blob_url      TEXT NOT NULL,          -- S3/Blob path
    content_hash  CHAR(64) NOT NULL,      -- SHA-256 of raw bytes
    uploaded_by   UUID NOT NULL,
    uploaded_at   TIMESTAMPTZ DEFAULT NOW(),
    classification VARCHAR(20) DEFAULT 'INTERNAL'  -- INTERNAL | CONFIDENTIAL
);
```

### 3.2 `solution_architecture_documents` table
```sql
CREATE TABLE solution_architecture_documents (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    story_id      VARCHAR(50) NOT NULL,
    document_id   UUID REFERENCES requirement_documents(id),
    version       INT NOT NULL DEFAULT 1,
    status        VARCHAR(20) DEFAULT 'DRAFT',  -- DRAFT | REVIEW | APPROVED | REJECTED
    content       JSONB NOT NULL,               -- Full structured SAD
    model_version TEXT NOT NULL,
    created_by    UUID NOT NULL,
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    approved_by   UUID,
    approved_at   TIMESTAMPTZ
);
```

### 3.3 SAD `content` JSONB Schema
```json
{
  "functional_requirements": [{"id": "FR1", "description": "..."}],
  "non_functional_requirements": [{"id": "NFR1", "category": "Security", "description": "..."}],
  "components": {
    "frontend": [{"name": "...", "purpose": "...", "source_reqs": ["FR1"]}],
    "backend_services": [{"name": "...", "purpose": "...", "source_reqs": ["FR2"]}],
    "databases": [{"name": "...", "type": "...", "source_reqs": ["FR3"]}],
    "apis": [{"endpoint": "...", "method": "...", "description": "..."}],
    "external_integrations": [{"name": "...", "purpose": "..."}],
    "security_components": [{"name": "...", "implementation": "..."}]
  },
  "architecture_decisions": [{"id": "ADR1", "decision": "...", "rationale": "..."}]
}
```

### 3.4 `audit_logs` table
```sql
CREATE TABLE audit_logs (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_type   VARCHAR(50) NOT NULL,   -- 'SAD_GENERATION'
    entity_id     UUID NOT NULL,
    action        VARCHAR(50) NOT NULL,
    user_id       UUID NOT NULL,
    model_version TEXT,
    input_hash    CHAR(64),
    output_hash   CHAR(64),
    duration_ms   INT,
    created_at    TIMESTAMPTZ DEFAULT NOW()
);
```

## 5. ArchGen Agent — Internal Design

### 5.1 Agent Module Structure (`agents/arch_gen_agent/`)
```
agents/arch_gen_agent/
├── __init__.py
├── agent.py               # Main agent class; LangGraph node definition
├── prompts/
│   ├── system_prompt.txt  # Persona + output schema instructions
│   ├── fr_extraction.txt  # Prompt for FR extraction
│   ├── nfr_extraction.txt # Prompt for NFR extraction
│   └── component_id.txt   # Prompt for 6-category component identification
├── validators/
│   ├── schema_validator.py  # Pydantic model for SAD JSON validation
│   └── completeness_check.py# Ensures all 6 AC2 categories present
├── parsers/
│   ├── pdf_parser.py      # PyMuPDF text extraction
│   └── docx_parser.py     # python-docx text extraction
└── tests/
    ├── test_agent.py
    └── golden_set/        # 5+ reference documents with expected outputs
```

### 5.2 Prompt Strategy
- **System prompt**: instructs LLM to act as a senior solution architect; mandates structured JSON output matching the SAD schema; prohibits invention of requirements not in the document.
- **Two-pass approach**: Pass 1 extracts FRs/NFRs. Pass 2 uses extracted requirements to identify components. This reduces context window pressure and improves precision.
- **Output validation**: Pydantic schema validation on every LLM response. If validation fails, retry once with error feedback injected into prompt (self-correction loop, max 2 retries).

## 6. Technology Choices
| Decision | Choice | Rationale |
|----------|--------|----------|
| Agent framework | LangGraph (existing in repo) | Consistent with platform pattern; supports stateful multi-step workflows |
| LLM | Azure OpenAI GPT-4o | Enterprise data boundary; high context window (128k) for large docs |
| PDF parsing | PyMuPDF (fitz) | Fast, accurate text + layout extraction; handles scanned docs with OCR fallback |
| DOCX parsing | python-docx | Lightweight; handles styles and tables |
| Output validation | Pydantic v2 | Type-safe; auto-generates JSON schema; integrates with FastAPI |
| API framework | FastAPI (existing) | Consistent with repo; async support; auto OpenAPI docs |
| Database | PostgreSQL + JSONB | Relational integrity for metadata; flexible JSON for SAD content |
| Cache | Redis | Idempotent generation for same document hash; response caching |
| Async task | Celery + Redis broker | Decouples long-running LLM calls from HTTP response cycle |
| Real-time updates | Server-Sent Events (SSE) | Lightweight push for generation progress without WebSocket complexity |

## 7. Non-Functional Design

### 7.1 Security
- All API routes protected by JWT middleware (`backend/middleware/auth.py`)
- RBAC: only users with `architect` or `admin` role can trigger generation
- Documents stored with server-side encryption; pre-signed URLs for download (15-min expiry)
- LLM API key rotated every 90 days via Secrets Manager
- Input sanitisation strips macros and scripts from DOCX; removes embedded objects from PDF before text extraction

### 7.2 Scalability
- Generation tasks dispatched to Celery worker pool; workers scale horizontally via Kubernetes HPA on CPU/queue-depth metrics
- Redis caches LLM response keyed by `SHA-256(document_content + prompt_version)`; avoids duplicate LLM calls for identical documents
- PostgreSQL connection pooling via PgBouncer

### 7.3 Observability
- Structured JSON logs emitted by all services (consumed by existing ELK/Datadog stack)
- Custom metrics: `arch_gen_duration_seconds`, `arch_gen_success_total`, `arch_gen_failure_total`, `llm_token_usage_total`
- Distributed tracing via OpenTelemetry; trace spans cover: document parse → prompt build → LLM call → validation → persist
- Alerting: P95 generation latency > 90s triggers PagerDuty alert

### 7.4 Versioning
- Prompts stored as versioned text files in `agents/arch_gen_agent/prompts/` and tagged in git
- SAD records store `model_version` and `prompt_version`; allows replay and comparison
- SAD document versioning: each re-generation creates a new version row; previous versions retained

## 8. Test Strategy

### 8.1 Unit Tests
- `test_pdf_parser.py` — validate text extraction from sample PDFs including edge cases (tables, multi-column)
- `test_docx_parser.py` — validate extraction from styled DOCX files
- `test_schema_validator.py` — valid and invalid SAD JSON inputs against Pydantic model
- `test_completeness_check.py` — scenarios with missing component categories

### 8.2 Integration Tests
- Mock LLM responses (recorded VCR cassettes) to test full agent pipeline without API cost
- Test API endpoints with TestClient: upload → generate → retrieve → approve flow
- Test Celery task execution with in-memory broker

### 8.3 Golden-Set Evaluation Tests (`agents/arch_gen_agent/tests/golden_set/`)
- Minimum 5 reference requirement documents spanning different domains (e-commerce, fintech, healthcare)
- Each paired with an expert-validated expected SAD
- Automated precision/recall scoring on component identification; must meet ≥85% precision (NFR2)
- Runs as part of CI on every PR touching agent code

### 8.4 End-to-End Tests
- Playwright tests covering: upload document → trigger generation → view SAD → edit SAD → approve
- Tested against staging environment with real LLM (small documents only; cost-controlled)

### 8.5 Security Tests
- OWASP ZAP scan on API endpoints
- Prompt injection test cases: documents containing `ignore previous instructions` patterns
- Verify encrypted storage via S3 bucket policy check in CI

### 8.6 Performance Tests
- Locust load test: 50 concurrent generation requests; assert P95 < 60s (NFR1, NFR6)
