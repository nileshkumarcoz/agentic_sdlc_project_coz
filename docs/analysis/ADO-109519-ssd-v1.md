### Component Responsibilities

| Component | File | Responsibility |
|---|---|---|
| Interface Layer | `interfaces/factorial_handler.py` | Accept raw user input; call validator; return formatted response or error |
| InputValidator | `utils/validator.py` | Parse & validate raw input; raise typed exceptions for invalid cases |
| FactorialService | `services/factorial_service.py` | Pure business logic — compute n! using iterative algorithm |
| ResponseFormatter | `utils/formatter.py` | Format result string (e.g., `"5! = 120"`) and error messages |
| Tests | `tests/test_factorial.py` | Unit + integration tests for all components |

## 2. Data Model

No persistent storage is required. All data is in-memory per request.

```python
# Input DTO
@dataclass
class FactorialRequest:
    raw_input: str          # exactly as received from user

# Output DTO
@dataclass
class FactorialResponse:
    success: bool
    n: int | None           # validated integer, None on error
    result: int | None      # n! value, None on error
    message: str            # formatted result string OR error message
```

## 5. Technology Choices

| Concern | Choice | Rationale |
|---|---|---|
| Language | Python 3.11+ | Repo primary language; built-in `int` supports arbitrary precision natively |
| Factorial Algorithm | Iterative loop (`math.factorial` or manual loop) | `math.factorial` is C-optimised in CPython; use it for performance |
| Data classes | `dataclasses.dataclass` | Lightweight DTOs without external dependencies |
| Testing | `pytest` + `pytest-cov` | Standard in Python agentic/AI repos; easy coverage reporting |
| Linting / Typing | `mypy` + `ruff` | Enforce type safety and code quality |
| CI Integration | Existing repo CI pipeline | No new tooling required; add test step to existing workflow |

## 6. Implementation — Core Logic

```python
# services/factorial_service.py
import math

SOFT_CAP = 10_000

def compute_factorial(n: int) -> tuple[int, str | None]:
    if n < 0:
        raise ValueError("n must be non-negative")
    warning = None
    if n > SOFT_CAP:
        warning = f"Warning: computing {n}! may take a moment for large values."
    return math.factorial(n), warning
```

```python
# utils/validator.py
class ValidationError(ValueError):
    pass

def validate_factorial_input(raw: str) -> int:
    stripped = raw.strip()
    if not stripped:
        raise ValidationError("Invalid input. Please enter a non-negative integer.")
    # Reject floats explicitly
    if '.' in stripped:
        raise ValidationError("Invalid input. Please enter a non-negative integer.")
    try:
        n = int(stripped)
    except ValueError:
        raise ValidationError("Invalid input. Please enter a non-negative integer.")
    if n < 0:
        raise ValidationError("Input must be a non-negative integer.")
    return n
```

## 7. Non-Functional Design

### 7.1 Security
- Input is always cast via `int()` after stripping — no `eval()` or dynamic execution.
- Length of raw string capped at 20 characters before processing to prevent DoS via enormous string parsing.
- No user data is persisted.

### 7.2 Scalability
- Stateless design: each call is independent; horizontally scalable if wrapped in an API.
- Soft cap at n = 10,000 with a warning; hard cap at n = 100,000 (configurable via env var `FACTORIAL_MAX_INPUT`) to protect CPU.

### 7.3 Observability
- Use Python `logging` module at `DEBUG` level within the service for input received and result computed.
- Errors logged at `WARNING` level with input value (sanitised) and error type.
- Integrate with existing repo's logging/monitoring setup.

## 8. Test Strategy

### 8.1 Unit Tests (`tests/test_factorial.py`)

| Test Case | Input | Expected Output |
|---|---|---|
| Zero factorial | `"0"` | `success=True`, result=`1`, message=`"0! = 1"` |
| Small positive | `"5"` | `success=True`, result=`120`, message=`"5! = 120"` |
| Large valid | `"20"` | `success=True`, result=`2432902008176640000` |
| Negative integer | `"-3"` | `success=False`, message contains `"non-negative"` |
| Float input | `"3.5"` | `success=False`, message contains `"Invalid input"` |
| Alpha string | `"abc"` | `success=False`, message contains `"Invalid input"` |
| Empty string | `""` | `success=False`, message contains `"Invalid input"` |
| Whitespace only | `"   "` | `success=False`, message contains `"Invalid input"` |
| One | `"1"` | `success=True`, result=`1` |
| Special chars | `"3!"` | `success=False`, message contains `"Invalid input"` |

### 8.2 Integration Tests
- Call `handle_factorial_request` end-to-end for all above cases.
- Assert `FactorialResponse` shape, types, and message format.

### 8.3 Coverage Target
- Minimum **90%** line coverage enforced in CI via `pytest --cov=. --cov-fail-under=90`.

### 8.4 Performance Smoke Test
- Assert `compute_factorial(1000)` completes in < 100 ms using `pytest-benchmark` or `time.perf_counter`.
